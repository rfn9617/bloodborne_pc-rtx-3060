## Совпадения и различия

| Область | Наша рабочая версия | Актуальный upstream | Решение |
|---|---|---|---|
| Векторы при смене размеров буферов | Постоянные targets по размеру, удаление неиспользуемых после 600 кадров | Linux тоже хранит несколько targets и удаляет заменяемый target отложенно | Фикс уже есть у нас; сохранить проверенный вариант |
| Камера | Выбор крупнейшего G-buffer, копия констант из GPU constant ring, ленивое чтение сигнатуры | Linux связывает камеру с G-buffer pass; сигнатура читается до проверки `pass_has_camera` | Реализации различаются; наше принятое ускорение не заменять автоматически |
| Texture GC | Бюджет тратится на удаления, возраст в секундах, ограниченная tiled write-back, дополнительные защиты | Linux и открытый Windows PR #4 исправляют расход бюджета на неудаляемые изображения | Основное исправление уже есть у нас |
| Shader cache | Есть запись во временный файл с переименованием, preload motion/driver pipelines | Linux дополнительно восстанавливается после повреждённой десериализации | Возможный перенос для стабильности и статтеров; не обещает больше FPS при прогретом кеше |
| Host-copy waits | `WaitHostCopies()` для записей игры | Linux имеет `NoteHostCopySource` / `WaitHostCopiesFor` | Первый отдельный CPU-кандидат |
| Presenter / прямые команды | `CommandBuffer()` ждёт поток записи | Linux умеет записывать presenter отложенно и выделять прямые сегменты | Следующие отдельные CPU-кандидаты |

Проверены также открытые PR. В Windows
[PR #4](https://github.com/Supermedo/bloodborne_pc/pull/4) и
[PR #5](https://github.com/Supermedo/bloodborne_pc/pull/5) пересекаются с нашими
исправлениями GC и `ProcessCommands`; применять их заново не нужно.
[PR #15](https://github.com/Supermedo/bloodborne_pc/pull/15) предлагает хранить
копии DCB/CCB отдельно до завершения coroutine. В нашей версии ещё есть общие
копируемые буферы: этот кандидат заслуживает отдельной проверки стабильности,
но прирост производительности от него не установлен. PR остаётся открытым.

Новая Linux-модель памяти использует dma-buf/mmap. В актуальном `run.sh` она
выключена по умолчанию и штатно ограничена AMD; NVIDIA обход экспериментальный.
Некоторые исторические абзацы `CHANGES_0.4.md` описывают более раннее состояние.
Для Windows RTX 3060 это отдельный перенос архитектуры, а не готовая настройка.

## Что происходит с DLSS и FSR

Quality действительно передаёт DLSS вход 1280×720 и получает 1920×1080.
Это 44,4 % от числа пикселей 1080p, но уменьшение пикселей не уменьшает весь
кадр в той же пропорции: геометрия, тени, CPU-трансляция, синхронизация,
часть compute и обработка после реконструкции имеют собственную стоимость.
Native AA апскейлера тоже следует отличать от режима без апскейлера.

Измеренный ранее профиль DLSS, 21 окно с выборочным GPU timing:

| Категория | Медиана, мс |
|---|---:|
| Весь измеренный GPU span | 12,860 |
| Сегменты `upscaler Run (DLSS)` | 1,886 |
| Resolve уменьшенных буферов в полные | 0,619 |
| Заполнение уменьшенных буферов | 0,142 |
| Image download | 1,056 |

Это интервалы с барьерами и вложенными операциями, не изолированная стоимость
нейросети. Медианы категорий нельзя складывать как точный разбор одного кадра.
Печатаются только 30 крупнейших labels. Несколько сегментов одной метки не
означают несколько вызовов DLSS. Профилирование само влияет на FPS.

В тяжёлых окнах с 1850–2200 отрисовками за кадр медианы составляют
83 уменьшенные отрисовки из 165 отрисовок сцены. Это счётчик, а не доля GPU-времени.
Он не включает всю геометрию теней/вспомогательных видов в понятие «сцена».

Код подтверждает причины смешанного разрешения:

- `SceneTargets::Eligible` масштабирует только подходящие targets 1920×1080
  и 960×540; размеры, слои, MSAA, feedback и несовместимые attachments могут
  оставить проход в исходном размере.
- `TemporalUpscaler::RasterScaling()` прекращает уменьшенную растеризацию
  после `done_this_frame`: последующая обработка использует полное изображение.
- `SceneTargets::SampleProxy()` не возвращает depth proxy для обычного sampling;
  доступ к native depth может потребовать resolve.
- `Rasterizer::DispatchRecord()` сохраняет исходные compute group dimensions.
  Группы нельзя сокращать произвольно: часть compute работает с буферами,
  не с экранными пикселями.
- `Run()` делает переходы native color/depth, читает proxy inputs и затем
  объединяет реконструированный RGB с исходной alpha в 1080p.
  Alpha нужна последующей обработке игры; удалить эту работу вслепую нельзя.

Сходное поведение DLSS и FSR делает общий путь рендерера обоснованным местом
исследования. Но одинаковый FPS сам по себе ещё не доказывает ошибку интеграции.
Обязательного прироста 20 % нет: экономия пиксельной работы может компенсироваться
стоимостью реконструкции и вспомогательных операций либо скрываться за другим
ограничением. AMD публикует ненулевую стоимость самого FSR, зависящую от GPU,
режима и выходного разрешения.
[AMD FSR 3](https://gpuopen.com/fidelityfx-super-resolution-3/).

Нет GPU-профиля нативного режима без апскейлера на идентичном кадре: пока нельзя
численно утверждать, какая именно категория съедает разницу native/Quality.

## Порядок следующих экспериментов

1. **GPU: сравнить два пути Quality.** Для 1080p `scripts/patches.py::scaled_sizes`
   автоматически выбирает proxy path даже при `live_resolution=0`.
   Уже существующий startup path можно запросить через `BB_RENDER_RES=1280x720`
   и `BB_OUTPUT_RES=1920x1080`: размер сцены задаётся самой игре, UI остаётся 1080p.
   Проверить его в отдельной копии на той же точке и с теми же эффектами.
   Это проверка архитектуры интеграции, а не новая DLL. Startup path использует
   `RunScaled` с LDR-входом позже в обработке, тогда как нынешний путь использует
   HDR `Run`; одинаковая картинка не гарантирована. Обязательны проверки волос,
   тумана, движения, прозрачностей, экспозиции, масок, интерфейса и frametime.

2. **CPU: перенос ожиданий по пересечению host-copy диапазонов.** Портировать
   минимальный набор из scheduler, buffer-cache producers и WRITE_DATA/DMA callers.
   Учесть все источники копий, нулевые/большие диапазоны, коллизии и завершение;
   неизвестные чтения должны давать консервативное ожидание. Сохранить режим
   полного ожидания для A/B. Тестировать совпадение данных при перезаписи источника,
   передачу памяти между потоками и порядок сигналов, затем gameplay и p99.
   GPU pending writes нашего принятого фикса сохраняются: это другая зависимость.

3. **CPU: presenter на рабочем потоке.** Перенести запись завершающих команд
   отдельно от первого CPU-кандидата. Проверить lifetime изображений/параметров,
   одновременную запись, submit/present ordering, resize и exit.
   В диагностическом тяжёлом ракурсе ожидания recorder/host copies уже малы
   (пример окна: 0,8 % / 0,6 %); крупный прирост от одного устранения этих ожиданий
   обещать нельзя. Измерять выигрыш именно на i7-11800H.

4. **GPU: выбрать дорогие оставшиеся native проходы.** Сопоставить shader hashes,
   фактический viewport, размеры attachments и timestamp. Для безопасного depth
   proxy sampling доказать корректность normalized coordinates, texelFetch,
   textureSize, LOD, compare/stencil и feedback. Оптимизировать конкретные
   дорогие проходы; число «неуменьшенных draws» само по себе недостаточно.

5. **CPU/GPU: прямые command segments и async submit из Linux.** Более широкий
   перенос планировщика после предыдущих независимых проверок. Прирост Linux
   на RX 7800 XT / RADV не прогноз для Windows/NVIDIA. Это параллелизм CPU-записи
   и отправки, его нужно отличать от GPU async compute.

6. **GPU async compute.** В нашей версии устройство создаёт одну очередь
   (`queueCount=1`), graphics и present ссылаются на неё; FSR/DLSS используют её же.
   Для перекрытия нужны другая очередь, независимая работа, timeline зависимости,
   проверка владения ресурсами при разных families и отдельные ресурсы для
   перекрывающихся кадров. Цепь scene → vectors → upscale → post зависима.
   Шейдерные ядра и bandwidth остаются общими: перенос всей реконструкции в другую
   очередь не гарантирует выигрыш. Начинать с одного доказанно независимого
   прохода, учитывать VRAM и задержку ввода.
   [Khronos: async compute](https://docs.vulkan.org/samples/latest/samples/performance/async_compute/README.html).

Bindless descriptors / прямые hooks libGnm могут уменьшить CPU-работу и копирование
в долгосрочной перспективе, но upstream пока описывает значительную часть этого
как следующий архитектурный шаг. Генерация кадров может повысить плавность
показа, однако не сокращает время расчёта реального игрового кадра: оценивать её
отдельно после базовых оптимизаций.

Для диагностики достаточно нескольких фиксированных конфигураций: native off,
DLSS Native AA, нынешний DLSS Quality, startup Quality; FSR Quality — дополнительная
проверка общего пути. Одинаковая точка/ракурс/сейв, прогретый кеш, неизменные эффекты,
векторы включены, лимит FPS снят только в тестовых копиях. Чистый FPS и редкое
GPU-профилирование — отдельные измерения. Сравнивать время кадра и p99, затем
проверять движение пользователем. Не менять сразу GPU и CPU варианты.

## Что не повторять

Ленивый native-input resolve уже проверен: убедительного выигрыша не было.
Пакетирование linear readbacks уже проверено: тяжёлая сцена 77,85 → 77,85 FPS,
p99 15,23 → 15,23 мс. Эти кандидаты не установлены. Новая стратегия readback должна
устранять доказанно ненужные операции по реальным CPU-чтениям, а не повторять batching.
